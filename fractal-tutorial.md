**Decisions that govern every run (mechanics → READMEs):**
- **★★★ SELECTION IS PROPOSE-THEN-SOLVE, BUILT ckpt 84.** `curation/recipes.py` (the recipe type) · `curation/candidate_ledger.py` (`curate candidate-ledger`) · `curation/solve.py` (`curate solve {run,sweep,truncate}`) · `curation/hunt.py` (`curate hunt {plan,run,merge,sheet,frames}`). Proven: all 128 same-recipe pairs in the backfill are byte-identical JPEGs. **Scores live in a sidecar keyed (recipe key, judge artifact, regime), never in the recipe's identity**, so a judge adoption invalidates scores and nothing else. Solver: `scipy.optimize.milp` (HiGHS) with a cutting-plane loop; **HiGHS gives a MIP no warm start at all** (measured — a live model with appended rows is 14.82 s against 14.87 s fresh), so incremental re-solve is a dead end and no second solver dependency was taken. What made it scale: a SOUND lower bound on the pixel-cloud metric (`mean|a−b| ≥ |mean a − mean b|` per direction per quantile block, 4 blocks shipped) which makes a WIDE screen free, plus fixing stage 2's columns against the incumbent floor (9.80 s → 0.36 s). ⚠ **A CORRELATED PROXY IS NOT A PRUNE** — location distance failed because colour comes from the map, not the place; only a lower bound is sound. Everything below about the GALLERY PASS is the record of gallery1–4, not the forward design. **TWO PHASES:** a run builds the POOL (harvest + judged small renders + a DIAGNOSTIC release); selection is `curate solve` over the candidate ledger. **THE GALLERY PASS AND `curate gallery` ARE DELETED (ckpt 84)** — git log is the only copy; read gallery1–4 as history. **★★ LOCATIONS ARE CUMULATIVE, CANDIDATES ARE PER-PASS (Matt, ckpt 78; BUILT ckpt 79):** the pass selects over the whole accumulated pool but seats ONLY candidates it made itself — a location is discovered ground, a candidate is a ~2 s recolour.
